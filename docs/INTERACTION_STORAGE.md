# 互动存储的实现选择

实现采用批准设计中的共库方案，在现有 `operations.sqlite3` 增加评论事实、写入上下文、收件箱事件和同步状态四张表。原 operations 表继续拥有发送权及回执。共库让 reservation 与请求上下文可以在同一 SQLite 事务提交，避免分库需要额外 outbox 才能恢复的目标缺口。

迁移使用 `PRAGMA user_version=1`，保留原表结构、UID 与操作 ID、指纹、状态、回执和原时间。旧日志只有指纹时，查询报告未知目标；匹配旧指纹的明确请求才可补绑定。未来数据库版本由旧工具拒绝，不覆盖其结构。没有数据库的本地查询不迁移、不创建状态。

生产表在设计草案上增加 `field_evidence_json`。该列保存每个字段的来源、观察时间及平台编辑版本，解决仅用 COALESCE 无法区分缺失字段、明确空文本、新编辑与旧回执的问题。`source_json` 聚合每个来源入口的首次和最近观察，平台创建时间单独保存。作者只取明确用户字段，自己的列表可在本次身份核验边界中补上自己的 UID。

独立验收补强了对话上下文与时间语义。peer 查询保留自己的开场及已知祖先，其他用户的上下文不进入该 peer 的轮数。history 使用平台消息时间倒序，没有时间时明确标示回执或首次观察依据；刷新不会把旧消息当作近期发言。公开与自己的列表都是平台正文来源，较新的编辑可更新正文而不降低既有作者和回复关系的公开证明。真实收件箱的 userid_a/userid_b 与 user_a/user_b 与旧字段共同支持。

身份建立证据存在 `interaction_sync_state` 的专用 identity 行，不增加第五张表。该证据允许普通单请求公开读取丰富已有账号历史；当前登录仍保持未核验标签。个人来源必须每次核验真实 UID。两个标志分别描述历史来源与当前读取，使自动公开读回兼容原 post 请求预算。

本地图片的实际上传 URL 在 reservation 时尚不存在。reservation 先绑定完整目标、正文及图片 SHA-256；上传结束后，评论 POST 前在共库短事务保存实际提交请求。该补充事务不扩大网络事务范围，失败时保留关闭的 reservation。外部 API 回执先提交，再生成可恢复投影。回执投影异常保留 returned 和原回执，查询或重放可以继续恢复。

完成回合查询采用不同 peer CID 的集合，而不是更新一个累加计数器。公开确认还要求字段来源明确观察到自己的 UID 和直接回复 CID。只有 CID 的稀疏公开节点不能自动确认回复关系。未解决操作与来信是否已有可见回复分别输出，防止类似回复错误关闭未知发送。

同步保留私有来源和根楼、深楼的阶段断点。最新私有页各读取一次后优先读取目标帖子，之后私有历史按各自的 offset 交替推进，防止巨大收件箱阻塞目标查询。每页合并与下一阶段位置共用一个事务；断点令牌绑定查询和账号，待深读根楼还检查本地帖子归属。现有接口无法证明目标全帖、全时间和所有来源的权威覆盖，所以即使来源遍历结束，`scan_finished` 也与 `history_complete` 分开。浏览快照继续放在 `browsing/snapshots.sqlite3`，不用旧快照作者或文本来猜历史发送目标。

实现只使用 Python 3.10+ 标准库，不复制隔离 SQLite 原型到生产路径，不修改 SDK。验证使用虚构 UID、CID 与网络 fixtures。执行 `python -m unittest discover -s tests -v` 和 `python tests/verify_portable.py` 可复现仓库内验收；这些检查不代表真实平台或独立验收。
