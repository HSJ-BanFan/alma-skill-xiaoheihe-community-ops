# 互动事实的 SQLite 存储

模块回答的是参与事实。agent 可以查询是否评论过某个帖子、与哪个用户讨论过、哪些输入已经回复，以及已确认完成了几轮。帖子和评论正文由当前平台读取提供，互动库只保存 ID、关系、时间与证据。

轮数返回 `count_semantics=public_verified_lower_bound`。已知自己的评论、明确 peer 关系、公开完成回合和根楼上下文完整性分别派生，缺失关系不会被转成从未讨论。同步候选来自已验证评论列表中的根楼 ID，状态和候选均从现有元数据推导，数据库仍使用版本 2。

## 共用发送数据库

互动表与现有 `operations` 表共用 `--data-dir/operations.sqlite3`。发送前的 reservation 和目标绑定在同一事务完成。同一次操作的内容指纹不同会被拒绝；相同指纹重放已有回执。读取和发送可以中断，恢复时仍能找到原来的 UID、操作 ID、帖子、根楼和回复目标。

另一种方案是独立的互动数据库，但两个 SQLite 文件不能共享同一个原子提交。该方案需要额外的 outbox 与恢复协议才能保证目标不丢失。当前工具在一台机器运行，共库保留现有发送边界，减少一套恢复流程。

## 保存的事实

| 表 | 保存的信息 | 用途 |
| --- | --- | --- |
| `operations` | UID、操作 ID、类型、请求指纹、发送状态、回执与更新时间 | 去重与发送结果恢复 |
| `interaction_write_context` | UID、操作 ID、帖子、根楼、回复目标、请求和提交指纹、投影时间 | 在没有原文的情况下恢复精确目标 |
| `interaction_comments` | UID 加 CID、帖子、根楼、作者 UID、直接回复 CID 和 UID、平台时间、观察时间与字段来源 | 参与、peer 查询与轮数计算 |
| `interaction_inbox` | 通知键、来信 CID、帖子、根楼、peer UID 与观察时间 | 查找来信的回复处置 |
| `interaction_sync_state` | UID、查询范围、身份核验证据、来源、预算和分页位置 | 继续有界同步与解释覆盖范围 |

正文、图片、媒体 URL、完整发送 payload 和原始收件箱 JSON 不进入四张互动表。发送核对使用 SHA-256 指纹，不能用它还原原文。传入节点和来源中的额外内容字段在存储边界被丢弃。信息流摘要按帖子批量查询结构化事实。

`operations` 按操作类型保存必要回执。独立上传的回执保留 CDN URL、对象位置、大小和尺寸，供同一操作 ID 查询或重放后继续组装发帖；该回执不包含图片数据。评论和回复回执只保留精确 ID 与状态，上传回执不会进入评论历史。

结构化表情消息的准备信息保存在同库的 `operation_messages` 附加表，与 reservation 同事务写入。它只保存精确目标、表情 ID、目录和渲染版本、内容摘要。此类回执附带文字、顺序和媒体地址列表的 SHA-256 摘要，便于后续核对；不保存原文或媒体 URL。原 `operations` 表保持七列，已有台账与互动版本 2 的迁移合同不变。

## 关系与确认状态

评论以 UID 加 CID 去重，帖子归属不可改写。自己的开场和祖先关系记录保留在 peer 查询中，其他用户的祖先仅用于说明关系，不计入该 peer 的轮数。

完成回合使用不同对方 CID 的集合。一个对方输入收到多个自己的回复，仍只计一轮。确认还要求公开入口明确给出自己的作者 UID、直接回复 CID，并且双方根楼一致且没有已知祖先循环。API 回执、自己的评论列表记录和公开精确读回分别保留，不把 unknown 当作从未参与。

点赞、收藏和取消收藏的发送事实用 `known_actions` 单独返回，不进入评论或轮数计数。它们描述历史操作，当前平台状态仍由当次平台读取决定。

平台创建时间与本地观察时间分开。history 优先按平台时间排序；缺少平台时间时明确标示回执或首次观察依据，刷新不会把旧评论当作新发言。字段来源独立合并，稀疏读取不会抹掉已有关系证明。

## 迁移与恢复

新库使用 `PRAGMA user_version=2`。实验版本 1 的迁移在事务内保留所有结构化关系和操作事实，删除旧正文、媒体、完整请求与原始通知列。原 operations 表的 UID、操作 ID、指纹、状态和时间保持不变。旧日志只有指纹时，目标仍为未知；匹配旧指纹的明确请求才可补绑定。未来数据库版本由旧工具拒绝。

迁移使用 SQLite `secure_delete` 清理删除记录，再进行 WAL checkpoint。并发读取持有旧快照时，WAL 清理可能延后。缺少数据库的本地查询不会创建目录或状态文件。原 operations 表存在但没有互动表的旧库可以查询，工具不会仅为一次空查询推测或创建历史。

回执先提交，评论事实另在短事务中投影。投影失败保留 returned 状态及回执，后续本地查询或重放可按精确 CID 恢复。提交指纹保存失败时，发送前的 reservation 保持关闭。网络请求不在 SQLite 写事务中执行。

## 运行边界

实现使用 Python 3.10+ 标准库 `sqlite3`，启用 foreign keys、WAL、FULL synchronous 和 busy timeout。SQLite WAL 允许读写并行，但同时只有一个 writer，数据库适合当前同机工具进程。多机器共享数据时需要服务端数据库，不能把 WAL 文件直接放在网络文件系统上。

同步先各读一页最新收件箱和自己的评论，再读取目标帖子的根楼与深楼，随后按各自的 offset 交替补读私有历史。每页事实和下一位置在同一事务保存。`scan_finished` 表示本次可取得的来源遍历结束，`history_complete` 仍为 false。

`post`、`comments`、`thread` 和 `inbox` 的当次输出继续提供完整内容。需要接着某条讨论时，agent 从 history 取得 CID，再用 `thread --around <CID>` 读取内容。显式选择的浏览快照及 asset 下载属于独立浏览功能，互动查询不会自动创建正文快照或下载图片。

行为和迁移验证使用虚构 UID、CID 与临时数据库。执行 `python -m unittest discover -s tests` 和 `python tests/verify_portable.py` 可复现仓库内检查。真实平台的登录身份、公开可见性和账号行为需要各自的运行证据。
